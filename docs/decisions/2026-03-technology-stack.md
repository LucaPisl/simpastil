## 1. Backend Runtime & Language

### Decision: Node.js 22 LTS + TypeScript 5

**Why Node.js:**
- Mature, stable ecosystem with a massive library surface. Security advisories are well-tracked via npm audit.
- Excellent async I/O performance for a CRUD-heavy API with no compute-intensive workloads.
- LTS (Long-Term Support) channel guarantees 30 months of security patches — no surprise end-of-life.
- Team familiarity is the highest-leverage factor for a solo/small project.

**Why TypeScript:**
- Catches entire classes of bugs at compile time (wrong field names, missing null checks, incorrect function signatures).
- Drizzle, Fastify, and Zod are TypeScript-first libraries — the type safety composes end-to-end from DB schema to HTTP response.
- `strict` mode + `noUncheckedIndexedAccess` eliminates most runtime type surprises.

**Alternatives considered:**

| Alternative | Reason rejected |
|-------------|-----------------|
| **Bun** | Promising but not production-proven at LTS stability level. Missing some Node.js compatibility features. Would add risk without meaningful gain for this workload. |
| **Deno 2** | Better security defaults but smaller ecosystem. Third-party library support for Drizzle/Fastify is lagging. |
| **Go (Gin/Echo)** | Would be faster for raw throughput, but the team is TypeScript-focused and there's no throughput problem to solve. Over-engineering. |
| **Python (FastAPI)** | Good for ML workloads. No advantage for this use case; async model is less ergonomic than Node.js for pure HTTP APIs. |
| **Rust (Axum)** | Maximum performance and memory safety, but prohibitive development overhead for a CRUD app. YAGNI. |

## 2. Backend Framework

### Decision: Fastify 5

**Why Fastify:**
- **Schema-first design:** Route definitions include a JSON Schema for input/output. `fast-json-stringify` serialises responses 2–5× faster than `JSON.stringify`. Input schema validation happens before the handler runs.
- **Plugin architecture:** `fastify.register()` with proper encapsulation prevents accidental global state leakage — each module is a self-contained plugin.
- **Async-first:** Every hook and handler is natively async — no callback-style workarounds.
- **Performance:** Benchmarks consistently show Fastify outperforming Express by 30–60% on simple routes. Not critical here, but it's free.
- **TypeScript support:** Fastify 5 ships with first-class TypeScript types; no `@types/fastify` package needed.

**Alternatives considered:**

| Alternative | Reason rejected |
|-------------|-----------------|
| **Express 5** | Still the most popular Node.js framework, but lacks built-in schema validation and is slower. Would require more manual wiring (body parsers, validation middleware) that Fastify provides out of the box. |
| **Hono** | Excellent for edge/serverless. Unnecessary complexity for a containerised server; ecosystem is smaller. |
| **NestJS** | Angular-style DI and decorators add significant boilerplate and magic. For a project of this scale, Nest's structure is over-engineered. Harder to audit. |
| **tRPC** | Excellent for TypeScript monorepos where client and server share types. Doesn't fit a native Flutter client; would require generating a REST adapter. |

## 3. ORM & Query Layer

### Decision: Drizzle ORM

**Why Drizzle:**
- **Zero runtime overhead:** Drizzle schemas are TypeScript types at compile time — no proxies, no reflection, no runtime metaclass magic.
- **Explicit SQL:** The query builder composes SQL that is inspectable and predictable. What you write is close to what executes.
- **Parameterised queries guaranteed:** Drizzle never constructs queries via string interpolation. This eliminates SQL injection as a class of vulnerability.
- **Schema as code:** The Drizzle schema file *is* the DB schema definition. Migrations are generated from schema diffs (`drizzle-kit generate`). No divergence between ORM model and actual table.
- **Lightweight:** No heavyweight connection pooling or ORM-level caching to misconfigure.

**Alternatives considered:**

| Alternative | Reason rejected |
|-------------|-----------------|
| **Prisma** | Excellent DX but generates a runtime engine (a Rust binary) that adds ~100MB to the container and has cold-start overhead. Schema-to-type flow is excellent but the `prisma.$queryRaw` escape hatch is too easy to reach and introduces injection risk. Overkill for this schema size. |
| **TypeORM** | Mature but complex. Decorator-based schema definition is hard to audit for security. Active Record pattern encourages fat models. |
| **Knex.js** | Good query builder but no type inference from schema — you still write types manually. Drizzle gives the same power with auto-inferred types. |
| **Raw `pg` / `postgres.js`** | Maximum control but requires writing parameterised queries by hand. Acceptable for tiny projects; high defect surface for a multi-table app. |
| **MikroORM** | Similar to TypeORM. Unit of Work pattern is excellent for complex domain logic but overkill here. |

## 4. Database

### Decision: PostgreSQL 16

**Why PostgreSQL:**
- **Row-Level Security (RLS):** Native, enforced at engine level. Even a compromised application layer cannot bypass RLS — it's the last line of defence for multi-tenant data isolation.
- **`gen_random_uuid()`:** Cryptographically random UUID generation is built-in (no `uuid-ossp` extension needed in PG 13+).
- **`INTEGER[]` columns:** Native array type for `schedules.frequency_days` — no serialisation/deserialisation required, and arrays are queryable with `@>` and `&&` operators.
- **`TIMESTAMPTZ`:** Time-zone-aware timestamps stored as UTC — eliminates an entire class of timezone bugs.
- **Reliability:** ACID compliance, well-understood failure modes, battle-tested at scale.
- **Ecosystem:** `pg_audit`, `pg_stat_statements`, and other monitoring extensions are production-ready.

**Alternatives considered:**

| Alternative | Reason rejected |
|-------------|-----------------|
| **MySQL 8 / MariaDB** | No native RLS. Array types require serialised JSON workarounds. TIMESTAMP handling is timezone-naive by default. |
| **SQLite (server-side)** | Single-writer bottleneck, no RLS, limited type system. Fine for the client; wrong for a shared server. |
| **MongoDB** | No RLS equivalent. Schema-less nature removes compile-time guarantees that Drizzle provides. Harder to audit data integrity. |
| **CockroachDB** | Distributed Postgres-compatible. Adds operational complexity without benefit at this scale (single node). |
| **PlanetScale** | Serverless MySQL. No RLS. Vendor lock-in. |

## 5. Authentication Strategy

### Decision: JWT (RS256) + Argon2id + Refresh Token Rotation

**JWT RS256:**
- **Asymmetric:** Private key signs, public key verifies. In a future multi-service architecture, verification services never need the private key. The private key has zero blast radius outside the auth module.
- **Stateless verification:** Fastify verifies the access token locally (no DB lookup per request). This keeps the hot path fast.
- **15-minute TTL:** Short enough that a stolen access token has a small window of validity. Long enough to avoid excessive refresh calls.

**HS256 explicitly rejected:**
- HS256 uses a single symmetric key for both signing and verification. Any service that can verify tokens can also forge them. This violates least-privilege. The requirement explicitly forbids HS256.

**Argon2id:**
- Winner of the Password Hashing Competition (2015). Resists both GPU-based brute-force (memory-hardness from Argon2i) and side-channel attacks (data-dependent memory access from Argon2d).
- Parameters: `time=3, mem=65536 (64MB), parallelism=4` — tuned so hashing takes ~300ms on the server. Slow enough to be unfeasible to brute-force; fast enough not to impact UX.

**Refresh token rotation:**
- Each use of a refresh token issues a new one and revokes the old. A stolen refresh token is invalidated the moment the legitimate user makes any request.
- Family-based invalidation: if a revoked token is replayed (stolen + used after rotation), the entire family is invalidated, forcing re-login. This detects theft retroactively.

**Alternatives considered:**

| Alternative | Reason rejected |
|-------------|-----------------|
| **Session cookies (server-side sessions)** | Requires server-side session store (Redis), adds latency to every request, harder to scale horizontally. JWT is appropriate for a mobile-first API. |
| **OAuth 2.0 / OIDC (third-party IdP)** | Adds complexity and dependency on external services. Appropriate for "login with Google" but not for a self-contained app with its own user store. |
| **bcrypt** | Still acceptable but loses to Argon2id on memory hardness. Argon2id is the NIST SP 800-63B recommendation. |
| **scrypt** | Memory-hard but lacks Argon2id's side-channel resistance and is not as well-audited. |
| **Paseto** | More opinionated token format, eliminates "algorithm confusion" attacks entirely. Valid choice; rejected because Fastify's JWT ecosystem is better-supported and RS256 with explicit algorithm enforcement achieves the same security goal. |

## 6. Input Validation Library

### Decision: Zod

**Why Zod:**
- **Runtime + compile-time:** Zod schemas are TypeScript types. `z.infer<typeof schema>` gives you the TypeScript type for free — no duplication between runtime validators and TypeScript interfaces.
- **Composable:** Schemas nest and extend cleanly. `schema.parse()` throws detailed, structured errors. `schema.safeParse()` returns a Result type for explicit error handling.
- **Integration:** Zod integrates directly with Fastify via `fastify-type-provider-zod`. The same Zod schema validates incoming JSON AND generates OpenAPI documentation.
- **Security:** All input is validated before any DB interaction. This eliminates injection via unexpected field types, oversized strings, or unexpected structure.

**Alternatives considered:**

| Alternative | Reason rejected |
|-------------|-----------------|
| **Joi** | Long-standing library but not TypeScript-first. Inferred types are less ergonomic. |
| **Yup** | Similar to Zod but slower. Zod has overtaken Yup in both performance and ecosystem. |
| **Fastify JSON Schema** | Fastify's built-in validation uses `ajv` under the hood and accepts JSON Schema. Generates faster validation but no automatic TypeScript type inference. Zod gives both without meaningful performance loss. |
| **class-validator** | Decorator-based. Requires `reflect-metadata`. Works well with NestJS but adds boilerplate with Fastify. |

## 7. Containerisation Strategy

### Decision: Docker + Docker Compose (single-host)

**Why Docker Compose:**
- Simple, reproducible local development and single-host deployment.
- Defines the full stack (nginx, api, db) in one file with a clear dependency graph.
- Named volumes for persistent DB data; bind mounts only for development.
- Internal bridge network (`pill-tracker-net`) ensures only nginx is reachable externally.

**Alternatives considered:**

| Alternative | Reason rejected |
|-------------|-----------------|
| **Kubernetes** | Massively over-engineered for a single-user pill tracker. Operational burden far exceeds benefit. |
| **Docker Swarm** | Reasonable middle ground, but Docker Compose is sufficient for this scale. |
| **Bare metal / systemd** | No environment isolation. Dependency conflicts. Hard to reproduce. |
| **PaaS (Railway, Render, Fly.io)** | Valid for managed deployment, but adds vendor lock-in and limits custom nginx config for TLS/security headers. |

## 8. Secrets Management

### Decision: `.env` file (gitignored) + Docker secret mounts for production

**Why this approach:**
- `.env` files are simple and universally understood. The key discipline is that `.env` is in `.gitignore` and never committed.
- For production, Docker secrets mount files into containers at `/run/secrets/` — the secret values are never in environment variables (which can leak via `/proc/self/environ`).
- **Zero secrets baked into images:** The Dockerfile contains no `ENV` with credentials. Images are safe to push to public registries.

**Alternatives considered:**

| Alternative | Reason rejected |
|-------------|-----------------|
| **HashiCorp Vault** | Enterprise-grade but enormous operational overhead for this scale. |
| **AWS Secrets Manager / GCP Secret Manager** | Cloud-provider lock-in. Overkill for self-hosted deployment. |
| **Hardcoded in docker-compose.yml** | Never acceptable. Credentials in source control. |

## 10. State Management

### Decision: Riverpod 2 (code generation)

**Why Riverpod:**
- **Compile-time safety:** `@riverpod` annotation + code generation produces typed providers. Accessing a provider that doesn't exist is a compile error, not a runtime crash.
- **Testability:** Providers can be overridden in tests without monkey-patching. Dependency injection is explicit.
- **No rebuild hell:** `ref.watch()` only rebuilds the widget subtree that depends on the changed state. `ref.read()` accesses state without subscribing.
- **AsyncNotifier:** First-class pattern for async state (loading / data / error) — maps directly onto API calls.

**Alternatives considered:**

| Alternative | Reason rejected |
|-------------|-----------------|
| **BLoC / Cubit** | More boilerplate. Event-driven model is excellent for complex state machines but overkill for CRUD. |
| **Provider** | Riverpod's predecessor. Riverpod fixes Provider's inheritance tree issues and adds compile-time safety. |
| **GetX** | Anti-pattern: mixes routing, state, and DI in one package. Hard to test, hard to reason about. |
| **MobX** | Observable/action pattern works well but requires code generation and is less idiomatic in Flutter. |

## 11. Local Database (Client)

### Decision: Drift (SQLite)

**Why Drift:**
- **Type-safe schemas:** Table definitions in Dart generate query helpers at build time. Wrong column names or types are compile errors.
- **Offline-first architecture:** SQLite is embedded, zero-latency, and works without any network. Drift's `StreamableQuery` provides reactive UI updates when data changes.
- **DAO pattern:** Data Access Objects separate query logic from business logic, making unit testing straightforward.
- **Migration support:** Drift's migration system handles schema evolution with version numbers and typed migration steps.

**Alternatives considered:**

| Alternative | Reason rejected |
|-------------|-----------------|
| **Hive** | Key-value store. Good for simple preferences, but structuring relational data (pills → schedules → logs) in Hive requires manual foreign key management. |
| **Isar** | Fast and type-safe, but NoSQL document model. Relationships require manual management. SQLite's relational model matches the server schema exactly. |
| **sqflite (raw)** | Drift is built on sqflite. Using raw sqflite means writing SQL strings by hand — higher defect surface, no type inference. |
| **ObjectBox** | Excellent performance but proprietary binary format. Drift's SQLite output is inspectable with standard tools. |

## 12. HTTP Client

### Decision: Dio + Custom Interceptors

**Why Dio:**
- **Interceptor chain:** Dio's interceptor system allows composing `AuthInterceptor` (attaches Bearer token), `RetryInterceptor` (auto-refresh on 401), and `LoggingInterceptor` (debug only) cleanly.
- **Token refresh logic:** The `AuthInterceptor` can queue concurrent requests while a token refresh is in flight, then replay them — no race conditions on simultaneous 401s.
- **Request cancellation:** Dio supports `CancelToken` — important for cancelling in-flight requests when navigating away.
- **Form data & multipart:** Handles future file upload needs (avatar images).

**Alternatives considered:**

| Alternative | Reason rejected |
|-------------|-----------------|
| **http (dart:http)** | Standard library client. No interceptors. Token refresh requires manual wrapping around every request. |
| **Chopper** | Good interceptor support but more boilerplate via code generation. Dio's API is more ergonomic for custom interceptors. |
| **Retrofit (flutter)** | Generates type-safe API clients from annotations. Would complement Dio, but adds build complexity. Can be added in v2. |

## 13. Secure Storage

### Decision: flutter_secure_storage

**Why flutter_secure_storage:**
- On Android, `flutter_secure_storage` uses the **Android Keystore System** — keys are stored in hardware (or a software-backed TEE) and never leave the secure environment. The application cannot extract the raw key material.
- Standard `SharedPreferences` stores data in a plaintext XML file on the device filesystem, readable by root or a forensic extraction — never acceptable for auth tokens.
- Supports biometric authentication gates (with `android:authenticationRequired`) for an optional enhanced security mode.

## 14. Notification System

### Decision: flutter_local_notifications

**Why flutter_local_notifications:**
- The only Flutter plugin that supports **exact alarm scheduling** on Android 12+ (requires `SCHEDULE_EXACT_ALARM` or `USE_EXACT_ALARM` permission).
- Pill reminders must fire at the exact scheduled time — inexact alarms (Android JobScheduler) can be batched and delayed by hours, which defeats the purpose.
- Supports Android notification channels (required for Android 8+), custom notification sounds, and action buttons ("Take", "Skip").

**Alternatives considered:**

| Alternative | Reason rejected |
|-------------|-----------------|
| **Firebase Cloud Messaging (FCM)** | Server-push notifications. Requires a running server and network. Pill reminders must work offline — local notifications are the right tool. |
| **awesome_notifications** | Feature-rich alternative, but flutter_local_notifications has wider adoption and better-tested exact alarm behaviour on Android 13+. |

## 15. Navigation

### Decision: GoRouter

**Why GoRouter:**
- **Declarative routes:** Route configuration is a data structure, not imperative `Navigator.push()` calls scattered throughout the codebase. Routes are auditable in one place.
- **Deep link support:** URI-based routing means the same route definition handles both internal navigation and external deep links (e.g., `simpastil://profiles/123/pills`).
- **Guard support:** `redirect` callbacks implement auth guards — unauthenticated users are redirected to login without per-screen checks.
- **Shell routes:** The `ShellRoute` widget wraps routes in a common scaffold (bottom nav bar) while maintaining the navigation stack correctly.
- **Riverpod integration:** `GoRouter` can observe a Riverpod `authStateProvider` and redirect automatically on auth changes.

**Alternatives considered:**

| Alternative | Reason rejected |
|-------------|-----------------|
| **Navigator 2.0 (raw)** | The underlying API that GoRouter builds on. Correct but extremely verbose to implement correctly. |
| **auto_route** | Code-generation based. Similar power to GoRouter. GoRouter is Flutter team-maintained and thus has better long-term support guarantees. |
| **get (GetX routing)** | Tied to GetX ecosystem. Avoided for the same reasons as GetX state management. |

## 16. UI System

### Decision: Material 3 + Custom Theming

**Why Material 3:**
- Provides a complete, accessible design system with semantics baked in (contrast ratios, touch targets, screen reader support).
- Material 3's `ColorScheme.fromSeed()` generates a harmonious full colour palette from a single seed colour — important for a health app where colour must be used for pill identification without being garish.
- Dynamic colour (Monet) on Android 12+ allows the app to match the user's wallpaper — reduces friction on Android where users expect platform-native aesthetics.

**Custom theming scope:**
- Override typography with a health-appropriate readable font (system default or `inter`).
- Per-pill colour swatches use the `color` field from the pill model, not Material 3 defaults.
- Dark mode support via `ThemeMode.system`.

## 17. Sync Architecture

> **Historical.** Superseded by the component-sync and medication-ledger
> contracts in [Architecture and contracts](../ARCHITECTURE.md).

### Decision: Delta Sync with Server-Wins Conflict Resolution

**Why delta sync:**
- **Bandwidth efficiency:** Only records modified since `clientLastSyncAt` are transmitted — not the entire dataset.
- **Batch endpoint:** A single `POST /sync` round-trip handles all entity types, minimising mobile radio wake events (important for battery life).
- **Soft-delete tombstones:** Client marks records as `is_deleted = true` instead of physically deleting. This ensures deletions propagate correctly even if the sync occurs days after the deletion.

**Why server wins:**
- Simplicity: deterministic, no user-facing merge UI required in v1.
- Health data context: the last authoritative action (taken/skipped) is typically the one on the server (logged from a different device), not an offline edit.
- Scaffold: the `sync_status = 'conflict'` column is a hook for a future CRDT-based per-field merge strategy.

**Alternatives considered:**

| Alternative | Reason rejected |
|-------------|-----------------|
| **Full sync (send everything)** | Wasteful for large dose_logs tables. Correct but inefficient. |
| **Event sourcing / append-only log** | More robust for complex conflict resolution but massively overengineered for this use case. |
| **CRDTs** | Theoretically correct for multi-device merge without a server round-trip. Too complex for v1; requires custom data structures for every field type. |
| **Last-write-wins by `updated_at`** | Server wins IS last-write-wins by server timestamp. The naming is changed because the server is the authority, not just the most-recent writer. |

## 18. TLS & Transport Security

### Decision: nginx as TLS Termination Proxy

**Why nginx in front of Fastify:**
- TLS termination in nginx is a well-understood, high-performance pattern. Fastify handles plain HTTP on the internal network — no TLS overhead in the application layer.
- nginx `limit_req_zone` provides IP-based rate limiting before requests reach application code — DDoS/brute-force is absorbed at the edge.
- nginx can be independently updated for TLS configuration changes (cipher suite updates, certificate rotation) without touching the Node.js application.
- Centralised place for HSTS, OCSP stapling, and security header configuration.

**Why TLS 1.3 only:**
- TLS 1.3 removes all weak cipher suites by design. No `ssl_ciphers` misconfiguration is possible — all valid TLS 1.3 cipher suites are secure.
- 0-RTT session resumption reduces reconnection latency for mobile clients.
- TLS 1.0/1.1 are deprecated by all major browsers and RFC 8996. TLS 1.2 support is unnecessary overhead for a new application.

## 19. API Versioning

### Decision: URL path versioning (`/api/v1/...`)

**Why URL versioning:**
- Explicit, cacheable, and inspectable in logs and nginx access logs.
- Client code (`Dio` base URL) is simple: `baseUrl = 'https://host/api/v1'`.
- Easy to run `v1` and `v2` simultaneously during a migration period by adding a new Fastify route prefix.

**Alternatives considered:**

| Alternative | Reason rejected |
|-------------|-----------------|
| **Header versioning** (`Accept: application/vnd.simpastil.v1+json`) | Harder to test, doesn't cache with CDNs, invisible in nginx logs. |
| **Query param versioning** (`?version=1`) | Leaks into query string; less clean. |
| **No versioning** | Not acceptable for an API with a mobile client that can't be force-updated. |

## 20. Monorepo vs. Polyrepo

### Decision: Monorepo (single repository, two top-level directories)

**Why monorepo:**
- `server/` and `flutter_app/` share no code directly (different languages), but coordination is high: API contract changes require simultaneous updates in both.
- A single repo allows one PR to cover both a server endpoint change and the corresponding Flutter client change — atomic, reviewable, and deployable together.
- Issue tracking, CI configuration, and documentation stay in one place.
- No overhead from cross-repo dependency management (there are no shared packages to publish).

**Alternatives considered:**

| Alternative | Reason rejected |
|-------------|-----------------|
| **Separate repos** | Increases friction for cross-cutting changes. Fine for large teams with independent release cycles; wrong for a solo/small project where frontend and backend evolve together. |
| **Nx / Turborepo monorepo tooling** | Adds value when there are shared TypeScript packages. No shared packages here — the tooling overhead is not justified. |
